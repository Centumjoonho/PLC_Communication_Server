# DB 저장 큐 변경

기존 `BlockingCollection<DbSaveItem>(500)`, DB Worker 하나, `EnqueueSave()` 호출 방식을 유지한다. 일반 데이터는 PLC+영업일별 항목에 최신값을 병합한다. 큐는 작업 순서를 전달하며, 아직 큐에 넣지 못한 항목도 `pendingSaveItems`와 로컬 파일에 남겨 나중에 처리한다.

## 변경 파일

- `Services/DbSaveService.cs`: 버전 비교, 순서대로 재처리, 5초 후 실패 재시도, 접수 데이터 로컬 보관, 정지 시 보존, 재시작 복원, 로그 제한.
- `Database/PlcDb.cs`: 오래된 Latest 덮어쓰기 방지, Daily 누적값 감소 방지, History ID 재사용, DB 대상별 보관함 식별자.
- `Services/PlcCollectionService.cs`: 접수 후 장애 이력 확정, 시작 시 미전송 누적값 복원, 정지 전 최종 Daily 인계. PLC 작업을 Task.Run으로 시작하여 로컬 파일 기록이 UI 스레드에서 실행되지 않게 함.
- `Services/RunRateService.cs`: 08시 초기화 직전 이전 영업일 최종값 인계, 누적값과 영업일을 같은 lock에서 복사.

## 동작

- 일반 상태: `S|PLC|영업일`, 초기화/정지 최종 Daily: `D|PLC|영업일`, 장애 이력: `H|Guid`.
- History 항목은 History만 저장한다. 당시의 오래된 상태로 Latest/Daily를 덮어쓰지 않는다.
- Worker가 데이터를 복사한 뒤 DB를 호출한다. 그동안 새 버전이 들어오면 저장 완료 후 새 버전을 지우지 않고 큐 뒤에서 다시 처리한다.
- 큐 버퍼가 500개여도 추가 접수 항목을 버리지 않는다. 일반 상태는 PLC 수에 비례하지만 장애 이력과 미전송 영업일은 실제 발생량대로 쌓인다.
- 전체 미저장 데이터를 처리하기 위해 Worker를 여러 개로 늘리거나 수집 주기를 5초로 변경하지 않았다.

## 로컬 보관과 정지

경로: `%LOCALAPPDATA%\RO_Server_Rebuild_2\DbPending\<DB 대상 해시>\*.json`

- DB 서버/포트/DB 이름/사용자별로 경로를 분리한다. 비밀번호는 저장하지 않는다.
- 접수 때 JSON을 임시 파일에 쓰고 Flush한 뒤 완성 파일로 교체한다. 정상 경로에서는 접수 반환 전에 디스크 기록이 완료된다.
- MySQL 저장 성공 후 동일 버전 파일만 제거한다. 재시도·복원 시 History ID는 동일하다.
- DB 장애 중 정지하면 미전송 파일을 남긴다. `[DB][STOP][DEFERRED]`는 MySQL 완료가 아니라 로컬 보관 후 정지라는 의미다. 다음 수집 시작 때 복원한다.
- 정지 처리에는 약 30초의 작업 시작 제한을 두며, 이미 진행 중인 DB 호출은 기존 연결/명령 Timeout을 따른다.
- 로컬 기록 실패 시 메모리에 보관하고 `[DB][LOCAL_PENDING][FAIL]`을 남긴다. DB에도 못 쓰고 파일에도 못 쓴 항목이 남으면 정상 종료 성공을 반환하지 않는다. 디스크 자체 장애나 강제 종료로 메모리만 남은 데이터를 보존할 수는 없다.
- 미전송 파일을 수동 삭제하면 데이터가 유실된다. 손상 파일 발견 시 자동 삭제하지 않고 시작을 중단한다.
- 장기 DB 장애에서는 장애 이력 파일/메모리가 늘어난다. 디스크 용량 및 오류 로그를 확인해야 한다. 저장 공간이 유한하므로 무기한 무손실을 보장하는 구조는 아니다.
- 정상 경로에서도 짧은 로컬 파일 기록 시간이 추가된다. 수집 작업은 백그라운드에서 실행하지만 운영 PC의 디스크 상태에 따라 소요시간을 확인해야 한다.
- 수집 시작 때 PLC 목록과 초기 DB 누적값을 조회하는 기존 동작은 유지한다. DB 없이 새로 수집을 시작하는 기능을 추가하지 않았다.
- 같은 영업일의 누적 가동초는 증가만 한다는 전제다. 운영 중 DB 수치를 수동으로 낮추는 작업은 로컬 미전송 데이터 및 메모리 상태와 함께 별도로 조정해야 한다.

## 검증

`tests/Run-DbSaveServiceTests.ps1`은 실제 DB와 PLC에 연결하지 않는다. 현재 서비스 소스를 가짜 DB와 함께 별도 컴파일한다.

- DB 저장 중 620개 갱신을 접수해도 일반 항목은 20개 유지.
- 저장 도중 새 버전 도착, 다른 PLC의 처리 기회, 개별 이력 보존.
- DB 장애 시 정지/파일 보존/새 서비스에서 누적값 및 이력 복원.
- DB 저장 성공 후 응답 유실을 흉내 내어 동일 ID 재시도 확인.
- 오전 8시 영업일 전환과 누적값/날짜의 일관된 복사.
- 손상 파일 보존 및 시작 거부.
- 큐 버퍼 500개를 채운 뒤 초과 이력까지 최종 처리.

실제 DB 서버의 지연 원인은 이 테스트로 확인할 수 없다. `[DB][SAVE][RETRY]`, `[DB][SAVE_QUEUE][STATUS]`의 시간과 실제 DB 로그를 함께 확인한다.
